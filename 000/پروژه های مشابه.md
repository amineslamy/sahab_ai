بر اساس جستجوی من در گیت‌هاب، **هیچ پروژه‌ای که دقیقاً ترکیب Go + PocketBase + Ollama + سه ورکر مجزا با صف‌بندی فایل** را پیاده‌سازی کرده باشد پیدا نکردم. اما چند پروژه بسیار مشابه از نظر معماری و الگوهای طراحی وجود دارد که می‌توانید از آنها الگو بگیرید:

## پروژه‌های مشابه برای الگوبرداری

### 1. **GraphMem-go** (Go + Knowledge Graph + Ollama)
**لینک**: [https://github.com/flancast90/GraphMem-go](https://github.com/flancast90/GraphMem-go)  
**وضعیت**: آخرین کامیت ژانویه 2026 (فعال)  
**شباهت‌ها**:
- پیاده‌سازی Go برای استخراج گراف دانش از متن
- استفاده از Ollama برای استخراج موجودیت‌ها و روابط
- ماژول `entity_resolver.go` برای تطبیق و ادغام موجودیت‌ها با شباهت‌سنجی معنایی
- حافظه عامل مبتنی بر گراف دانش

**تفاوت‌ها**: از PocketBase استفاده نمی‌کند، مستقیماً با SQLite کار می‌کند. [libraries](https://libraries.io/go/github.com%2Fflancast90%2FGraphMem-go)

***

### 2. **simple-graph-builder** (Entity Resolution Pipeline)
**لینک**: [https://github.com/junhewk/simple-graph-builder](https://github.com/junhewk/simple-graph-builder)  
**وضعیت**: آخرین ریلیز می 2026 (108 کامیت، فعال)  
**شباهت‌ها**:
- پایپ‌لاین چندمرحله‌ای تطبیق موجودیت (Entity Resolution) دقیقاً مشابه طرح شما:
  - کش پایدار (Persistent cache)
  - تطبیق نام دقیق (Exact name hash lookup)
  - تطبیق مترادفات (Alias match)
  - شباهت‌سنجی Embedding (Cosine > 0.90 = auto-merge)
  - تأیید LLM برای موارد مبهم (0.80-0.90)
- پشتیبانی از Ollama برای پردازش محلی
- استخراج JSON ساختاریافته از متن

**تفاوت‌ها**: پلاگین Obsidian است (TypeScript)، نه Go. اما **الگوریتم تطبیق آن دقیقاً همان چیزی است که شما در Worker 3 نیاز دارید**. [github](https://github.com/junhewk/simple-graph-builder)

***

### 3. **semantica** (Full Knowledge Graph Pipeline)
**لینک**: [https://github.com/semantica-agi/semantica](https://github.com/semantica-agi/semantica)  
**وضعیت**: آخرین کامیت 7 سپتامبر 2026 (2868 کامیت، بسیار فعال)  
**شباهت‌ها**:
- پایپ‌لاین کامل: Ingest → Parse → Normalize → Split → Extract → Conflict Detection → Deduplication → Knowledge Graph
- ماژول `semantica.deduplication` برای تطبیق موجودیت‌ها با Blocking + شباهت معنایی
- ماژول `semantica.normalize` برای نرمال‌سازی نام‌ها (تبدیل حروف، حذف اعراب)
- ماژول `semantica.conflicts` برای تشخیص تضادها قبل از ادغام
- پشتیبانی از چندین منبع (فایل، وب، دیتابیس)

**تفاوت‌ها**: پایتون است، نه Go. اما **مستندات Architecture.md آن بهترین مرجع برای طراحی پایپ‌لاین شماست**. [github](https://github.com/semantica-agi/semantica)

***

### 4. **NexusRAG** (Go + Ollama + Knowledge Graph)
**لینک**: [https://github.com/LeDat98/NexusRAG](https://github.com/LeDat98/NexusRAG)  
**وضعیت**: مارس 2026 (فعال)  
**شباهت‌ها**:
- ترکیب جستجوی برداری + گراف دانش (LightRAG)
- استفاده از Ollama برای استخراج موجودیت/رابطه
- پردازش اسناد (PDF, DOCX, etc.)
- معماری هیبرید برای بازیابی

**تفاوت‌ها**: از Neo4j یا FalkorDB استفاده می‌کند، نه PocketBase. [github](https://github.com/LeDat98/NexusRAG)

## الگوهای کلیدی برای پیاده‌سازی شما

### الگوریتم Entity Resolution (از simple-graph-builder)
```go
// مرحله 1: کش دقیق
if cached := resolutionCache.Get(cleanName); cached != nil {
    return cached.EntityID
}

// مرحله 2: تطبیق دقیق نام
entity, err := pb.FindEntityByCleanName(cleanName, entityType)
if err == nil {
    return entity.ID
}

// مرحله 3: تطبیق مترادفات
alias, err := pb.FindAliasByAliasName(cleanName)
if err == nil {
    return alias.EntityID
}

// مرحله 4: شباهت Levenshtein (فقط برای هم‌نوع‌ها)
similarEntities, _ := pb.FindEntitiesByType(entityType)
bestMatch := FindBestLevenshteinMatch(cleanName, similarEntities, threshold=0.85)
if bestMatch != nil {
    // ثبت به عنوان alias جدید
    pb.CreateAlias(bestMatch.ID, cleanName)
    return bestMatch.ID
}

// مرحله 5: ایجاد موجودیت جدید
newEntity := pb.CreateEntity(cleanName, entityType, attributes)
resolutionCache.Set(cleanName, newEntity.ID)
return newEntity.ID
```

## توصیه‌های معماری برای PocketBase

### 1. بهینه‌سازی SQLite برای هم‌زمانی
PocketBase بر پایه SQLite است. برای جلوگیری از قفل شدن دیتابیس در نوشتن هم‌زمان:
- از **صف نوشتن تک‌نخی** (single-threaded write queue) در Worker 3 استفاده کنید
- تمام عملیات INSERT/UPDATE را به یک goroutine کانال‌بندی کنید [zinruss](https://www.zinruss.com/pocketbase-sqlite-lock-contention-edge-optimization/)

```go
// در Worker 3
type WriteOp struct {
    Entity   *Entity
    Relation *Relation
    Callback chan error
}

var writeQueue = make(chan WriteOp, 1000)

go func() {
    for op := range writeQueue {
        // فقط یک goroutine می‌نویسد
        err := pb.Save(op.Entity)
        op.Callback <- err
    }
}()
```

### 2. ایندکس‌گذاری بهینه
```sql
-- در PocketBase Console یا API
CREATE INDEX idx_entities_clean_name ON entities (clean_name);
CREATE INDEX idx_aliases_alias_name ON aliases (alias_name);
CREATE INDEX idx_relations_source ON relations (source_entity_id);
CREATE INDEX idx_relations_target ON relations (target_entity_id);

```

### 3. الگوی Retry برای Ollama
```go
func callOllamaWithRetry(chunk string, maxRetries int) (*ExtractionResult, error) {
    for i := 0; i < maxRetries; i++ {
        result, err := callOllama(chunk)
        if err == nil && result.IsValid() {
            return result, nil
        }
        time.Sleep(time.Duration(i+1) * time.Second) // backoff
    }
    return nil, fmt.Errorf("failed after %d retries", maxRetries)
}
```

## جمع‌بندی

**پروژه‌ای دقیقاً مشابه طرح شما وجود ندارد**، اما می‌توانید از این الگوها استفاده کنید:

| بخش | پروژه مرجع | الگو |
|-----|-----------|------|
| Entity Resolution | simple-graph-builder | کش 7 مرحله‌ای + Levenshtein |
| پایپ‌لاین استخراج | semantica | Ingest → Extract → Dedup → KG |
| Go + Ollama | GraphMem-go | استخراج گراف با Go |
| پردازش اسناد | NexusRAG | چانکینگ + استخراج JSON |

**نکته کلیدی**: طرح شما از نظر **سه ورکر مجزا با صف‌بندی فایل** نوآورانه است و هیچ پروژه‌ای این معماری را عیناً پیاده‌سازی نکرده. این یک مزیت است چون برای مقیاس‌پذیری آفلاین طراحی شده.
